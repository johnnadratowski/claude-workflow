# Inter-Agent Communication

A lightweight mailbox + tmux-bridge that lets Claude Code sessions running in different tmux panes message each other. Useful when you're working in one worktree and want a peer agent in another worktree to take on a sub-task and report back.

## Branch coordination model (purely local)

The agent fleet coordinates on the **local** base branch — `WORKFLOW_BASE_BRANCH` in `.claude/workflow.config` — never `origin/<base>`. All worktrees on the machine share one `.git`, so `refs/heads/<base>` is a single shared ref every agent reads and advances — a peer's work is mergeable the moment it's *committed* (no push needed).

**`origin/<base>` is pushed by exactly one skill: `/base-push`.** It publishes local `<base>` to `origin/<base>` (a one-way snapshot for backup / CI / other machines) when — and only when — a human runs it. The PR lifecycle skills make their own **deliberate, user-gated** origin writes — `/open-pr` pushes frozen `pr/*` branches and `/pr-comments` posts approved replies — but neither ever touches `origin/<base>`. There is **no pull skill** (the former one was removed), so origin is effectively write-only for the base (the PR skills fetch the PR-target branch explicitly before cutting a `pr/*` branch). If you ever need to ingest published remote state into `<base>`, that's a deliberate manual `git fetch` + merge.

| Skill | Touches `origin`? | Role |
|-------|-------------------|------|
| `/base-merge` | no | Local sync of `<base>` ↔ a feature branch (down/up). |
| `/base-pr` | no | Review + promote fixes into **local** `<base>` (or any `--base`). |
| `/base-test` | no | Merge **local** `<base>` in, run the gate sweep. |
| `/base-push` | **yes (publish only)** | Land a branch into local `<base>`, then `git push origin <base>`. |
| `/open-pr` | **yes (`pr/*` only, user-gated)** | Fetch the PR target, push a frozen `pr/*` branch, `gh pr create` after user approval. Never `origin/<base>`. |
| `/pr-comments` | **yes (comments only, user-gated)** | Post the approved reply package + resolve threads on a PR. Never pushes refs except the `pr/*` head update in its approved package. |

All merges into `<base>` go through the canonical **local** transient-worktree helper `merge_into_branch_local` (defined in `.claude/scripts/merge-helpers.sh`, sourced by every base-* skill) — a throwaway worktree checked out on `<base>` so the merge never disturbs the caller's worktree, with no fetch and no push. Consequence: local `<base>` is normally *ahead* of `origin/<base>`; that's the expected steady state, not drift. Never check out the literal `<base>` branch in a worktree (it breaks `worktree add <base>` for everyone) — the command-and-control agent rides a dedicated `<base>-cc` branch (or a detached `origin/<base>`) for a base-tracking worktree.

## How it works

1. **Auto-registration.** `.claude/hooks/register-agent.sh` writes a file at `~/.claude/running-agents/<name>.<pid>` containing the session's `$TMUX_PANE`. The hook is wired in **user-level** `~/.claude/settings.json` for `SessionStart` — a deliberate placement, **not** a Claude Code limitation (project-local `SessionStart` hooks fire fine in current Claude Code; `cc-watcher-keepalive.sh` is wired project-locally on exactly that event): user-level wiring makes registration run in every project the engineer launches `claude` in, resolving via `$CLAUDE_PROJECT_DIR` so it's a clean no-op where the script doesn't exist. The hook resolves the claude PID by parsing `session_id` from its stdin JSON and finding the `~/.claude/sessions/<pid>.json` whose contents match, then verifying the PID is alive and belongs to a `claude` process (session files accumulate across runs, so blind trust gives stale PIDs). Falls back to walking the process tree, then to `$PPID`. Agent name comes from the session file's `name` field (set by `/rename`; persists across resumes), then current git branch (sanitized: `/` → `-`), then cwd basename. The hook also sets the tmux pane title, renames the tmux window **for window-owning roles only** (`coordinator`/`feature` — `review` and `test` agents share one window across panes, so their pane must not rename it; role via the `~/.claude/agents/<name>.role` override or the `fleet_resolve_role` name classifier in `.claude/scripts/_fleet.sh`), and (on first startup) types `/rename <name>` so Claude's own session label, the tmux pane border (if `pane-border-status` is enabled), and the tmux tab all converge. Every invocation appends a line to `~/.claude/debug/register-agent.log` for troubleshooting.
2. **Base-branch tracking.** `~/.claude/agents/<name>` is a persistent file (one per agent) recording the git branch the agent considers its "home." First registration writes the current branch. On every subsequent registration, the hook compares stored vs. current; on mismatch it emits `hookSpecificOutput.additionalContext` so the model surfaces the warning to the human ("you're on branch X but agent N was registered with base branch Y — switch back?"). `/agent-rename <new>` renames the local git branch via `git branch -m`, updates this file, and renames everything else (registry, tmux, Claude session name) in lockstep.
3. **Role context (per-type startup instructions).** On `SessionStart`, the hook derives the agent's **role** from its name via **dash-delimited segment matching** (see `resolve_role()` in `register-agent.sh` — the canonical patterns; `x-print` is NOT review): a `test` segment → `test`, a `pr`/`review` segment → `review`, a `cc`/`coordinator` segment → `coordinator`, else `feature` (override per-agent with a single word in `~/.claude/agents/<name>.role`) — reads `.claude/agent-roles/<role>.md` from the repo, and injects it via the same `additionalContext` payload as the base-branch warning. So a review agent boots already primed to review, a test agent to run the gate sweep, a feature agent to implement + doc-sync + hand off, etc. Edit the role files to change what each type is told; they ship with the repo, so changes propagate via merge-down and take effect on each agent's **next session start**.
3. **Sending.** `/agent-send <target> --stdin [--reply|--followup] <<'BODY'…BODY` (or the legacy `<target> "<body>"` form) first runs `register-agent.sh send-selfheal` as a prelude (idempotent — fast-path no-op when own entry is current) so a stale or missing own-entry is rebuilt before the send proceeds. Then writes the body to the recipient's **per-recipient mailbox** `~/.claude/agent-inbox/<target>/<uuid>.<self>.<kind>.txt` (kind = `req`|`rep`|`fwd`), verifies the target's PID and tmux pane are still alive (pruning stale registry entries when not), and delivers `/agent-msg <self> <target>/<uuid>.<self>.<kind>.txt [reply|followup]` into the target's pane via `tmux send-keys`. The file write is the durable delivery; the send-keys is only a latency optimization, and it is **skipped** in two cases — the drain delivers instead: (a) the target pane is in **copy-mode** (scrolled back), where the nudge would be swallowed; (b) the target is **busy mid-turn** (a fresh `~/.claude/agent-busy/<target>` marker — set by `mark-busy.sh` on the target's `UserPromptSubmit` and re-touched on its every `PreToolUse` (so notification/continuation turns count as busy too), cleared by its drain on `Stop`); (c) the target is **held on a Monocle interactive wait** (`~/.claude/agent-hold/<target>`, see below). Skipping a busy/held target costs no latency — it can't act before its next `Stop` anyway, and the drain delivers there. The busy-skip alone can't fully prevent the **duplicate** a buffered nudge + drain would produce, though — the `agent-busy` marker is a heuristic that goes stale on a long (>5 min) turn and races the idle→busy boundary. So whenever the live nudge **does** fire, agent-send also drops a **delivery-claim** (`~/.claude/agent-nudge-claim/<uuid>.<sender>.<kind>.txt`): the target's Stop-drain **defers** any message with a fresh claim (the buffered `/agent-msg` owns delivery), and a stale claim (>2 min — nudge lost, or a long turn) is reclaimed and delivered. This makes the two paths mutually exclusive per message, so a message is delivered exactly once and never stranded (worst case a ≤2 min delay). The claim is released on delivery by `agent-msg.sh`; a residual straggler for an already-delivered file is a **silent** no-op (the `agent-msg` skill prints no banner on a gone file). **Prefer the `--stdin`/heredoc form for any non-trivial body:** passing the body as an argv string lets the *caller's* shell expand backticks / `$(...)` inside it before agent-send runs, which silently corrupts the message (it mangled a code review in practice); a quoted heredoc is immune.
4. **Receiving.** The slash command `/agent-msg <sender> <filename> [reply|followup]` lands in the recipient's prompt buffer. The `agent-msg` skill body instructs the recipient to read + delete the message file, print a visible banner so the human watching the terminal sees that input came from a peer agent, then act on it: a **request** or **followup** is processed and answered (followup = a reply that *does* expect a response); a **reply** is just integrated (no response, breaking ping-pong loops).
5. **Reliable drain (no lost messages).** `tmux send-keys` is best-effort — if the recipient is mid-turn, sitting in a permission prompt, or scrolled back, the nudge can fail to register and the `/agent-msg` line never runs. So the body is staged in a **per-recipient** mailbox and `.claude/hooks/drain-inbox.sh` (wired as a project-local `Stop` hook) runs at the end of every turn: it discovers the agent's own name via `$TMUX_PANE` (self-healing a drifted/missing registration the same way `agent-send` does, lazily, if the scan comes up empty), scans `~/.claude/agent-inbox/<self>/` and, for any undrained message, blocks the stop and re-injects the exact `/agent-msg <sender> <path> [reply|followup]` (reconstructed from the filename — sender + kind are encoded in it, oldest-first by mtime). A lost nudge is therefore a *delayed* message, never a lost one. Loop-safe: the `agent-msg` skill deletes each file it processes (next Stop finds an empty mailbox), and the drain never re-blocks when `stop_hook_active` is already set. The drain also **GCs abandoned messages** (default >7 days, `AGENT_INBOX_GC_DAYS`) that pile up in mailboxes of agents that never drain.
6. **Cleanup.** `SessionEnd` removes the per-session registry file (`<name>.<pid>`) but leaves the persistent `~/.claude/agents/<name>` base-branch record. PID-not-alive checks at send time prune stragglers from unclean exits. Message files are removed by the recipient when processed; the per-recipient mailbox dir is created lazily on first send. A mailbox is **not** deleted on `SessionEnd` (the agent may resume and still need its messages) — truly-abandoned files are reaped by the drain's time-based GC instead.
7. **Waking parked agents.** The drain covers any agent that takes another turn, but a fully idle agent has already Stopped and won't run its drain until woken. `.claude/scripts/inbox-watcher.sh` closes that gap: a poller the **coordinator keeps alive automatically** (`cc-watcher-keepalive.sh` — SessionStart launch + Stop self-heal, one instance machine-wide) that re-nudges live recipients with the reconstructed `/agent-msg` for any message left sitting past a timeout, throttled per message via the delivery-claim's age (the message file's mtime is never bumped, so drain ordering and the GC clock stay truthful). Two guards keep it from spamming an agent that is slow rather than idle: it **skips a held recipient** (`~/.claude/agent-hold/<name>` — parked on a Monocle verdict wait; see below), and it **caps re-nudges per message** at `WORKFLOW_MAX_REDELIVER` (default 3), after which it backs off and leaves the message for the lossless Stop-drain. The cap covers **any** long block (e.g. a 20-min test run, whose single tool call trips the same 5-min `agent-busy` staleness), not just Monocle. The redelivery count rides in the message's delivery-claim file (released on delivery, so it never leaks).

## Layout

| Path | Role |
|------|------|
| `.claude/hooks/register-agent.sh` | Idempotent registration script. Wired as `SessionStart` in user-level `~/.claude/settings.json`; also invoked as a self-heal prelude by `agent-send.sh` and `agent-rename.sh`. On `SessionStart` it also injects role context (below) via `additionalContext`. |
| `.claude/agent-roles/<role>.md` | Per-role startup instructions (`feature`/`review`/`test`/`coordinator`) injected at `SessionStart` based on the agent's name. Edit to change what each agent type is told. |
| `~/.claude/agents/<name>.role` | **Optional, per-machine.** One word; overrides the name-derived role for that agent. |
| `.claude/hooks/mark-busy.sh` | `UserPromptSubmit` + `PreToolUse` hook (project-local settings) — touches `~/.claude/agent-busy/<name>` so peers' `agent-send` skips the redundant nudge while this agent is mid-turn. Cleared by `drain-inbox.sh` (Stop) and `unregister-agent.sh` (SessionEnd). Also sets/clears the **hold** marker `~/.claude/agent-hold/<name>` by inspecting the tool payload — set on the blocking `mcp__monocle__get_feedback(wait=true)` call, cleared by any other tool call / prompt (so peers stop nudging an agent parked on a human Monocle verdict, whose `agent-busy` marker would otherwise go stale after 5 min). |
| `.claude/hooks/unregister-agent.sh` | `SessionEnd` hook in project-local settings — remove the per-session registry file. Send-time `kill -0` is the safety net for unclean exits. |
| `.claude/hooks/drain-inbox.sh` | `Stop` hook in project-local settings — drains this agent's per-recipient mailbox, re-injecting any `/agent-msg` the live nudge dropped. Makes delivery at-least-once. Also GCs abandoned messages and lazily self-heals a drifted registration. |
| `.claude/hooks/drain-inbox.test.sh` | Hermetic test suite for the drain (run: `bash .claude/hooks/drain-inbox.test.sh`). Locks in the empty-mailbox, dot-delimiter, GC, kind-parse, and self-heal invariants. |
| `.claude/scripts/agent-send.sh` | Backing script for `/agent-send` (supports `--stdin` heredoc bodies, `--reply`, `--followup`) |
| `.claude/scripts/agent-broadcast.sh` | Backing script for `/agent-broadcast` — fan-out to all live peers |
| `.claude/scripts/agent-fanout.sh` | Backing script for `/agent-fanout` — `status` / `merge-down` / `send` / `restart` (allow-listed; `restart` needs `--yes`) |
| `.claude/scripts/agent-msg.sh` | Backing script for `/agent-msg` — read+delete one message, or `drain` the whole mailbox (allow-listed, so no ad-hoc `cat`+`rm`) |
| `.claude/scripts/inbox-watcher.sh` | The **coordinator-run** poller that re-nudges parked (already-Stopped) agents **and retriable-errored agents** (rate-limit / overloaded / server-error StopFailure marker) to continue — covers the idle-fleet gap the drain hook can't. The cc keeps exactly one instance alive via the `cc-watcher-keepalive.sh` hook (SessionStart launch + Stop keep-alive). Pure send-keys, no model calls. |
| `.claude/scripts/agent-rename.sh` | Backing script for `/agent-rename` |
| `.claude/skills/agent-msg/SKILL.md` | Receiver-side handler (banner + request/reply/followup branching) |
| `.claude/skills/agent-send/SKILL.md` | Sender-side dispatcher |
| `.claude/skills/agent-broadcast/SKILL.md` | Fan-out dispatcher (carries an explicit user-authorization gate) |
| `.claude/skills/agent-fanout/SKILL.md` | Fleet orchestration — status / role-targeted fan-out / merge-down / idle-gated restart |
| `.claude/skills/agent-rename/SKILL.md` | Rename current agent (registry + tmux + claude session + git branch + base-branch file) |
| `~/.claude/running-agents/<name>.<pid>` | **Runtime, never tracked.** Per-session registry. Filename carries the claude PID; contents are the tmux pane id. Cleaned up on `SessionEnd`. |
| `~/.claude/agents/<name>` | **Persistent.** Agent's recorded base git branch. Written on first registration; consulted on every subsequent SessionStart to detect "you're on the wrong branch" drift. Updated by `/agent-rename`. |
| `~/.claude/agent-inbox/<recipient>/<uuid>.<sender>.<kind>.txt` | **Runtime, never tracked.** Per-recipient mailbox; `<kind>` is `req`\|`rep`\|`fwd`. In-flight message bodies, deleted by the recipient after read; undrained ones are re-injected by `drain-inbox.sh`, and abandoned ones (>7d) are GC'd by it. |
| `~/.claude/agent-busy/<name>` | **Runtime, never tracked.** Present (and fresh, <5 min) while the agent is mid-turn. Lets a sender skip the redundant live nudge for a busy target. Set on `UserPromptSubmit` + every `PreToolUse`, cleared on `Stop`/`SessionEnd`. |
| `~/.claude/agent-hold/<name>` | **Runtime, never tracked.** Present while the agent is blocked on a **Monocle interactive verdict wait** (`get_feedback(wait=true)`) — a single long tool call whose `agent-busy` marker goes stale, so this outlives it. `agent-send` + `inbox-watcher` suppress **all** nudges to a live held agent (message drains once at its next `Stop`). **No** staleness cap (a human review can run for hours) — bounded instead by liveness + the clears: set/cleared by `mark-busy.sh` per tool call, plus `Stop` (drain) and `SessionEnd` (unregister) backstops. |
| `~/.claude/agent-nudge-claim/<uuid>.<sender>.<kind>.txt` | **Runtime, never tracked.** A per-message **delivery-claim**: dropped by `agent-send`/`inbox-watcher` when they live-nudge, so the recipient's Stop-drain **defers** that message (the buffered `/agent-msg` owns it) instead of injecting a duplicate. A stale claim (>2 min) is reclaimed by the drain; released on delivery by `agent-msg.sh`; GC'd (>7 days) as a backstop. |
| `~/.claude/debug/register-agent.log` | Diagnostic log; one line per hook invocation with source, PID-discovery path, and outcome. |

## Slash commands

| Command | Use |
|---------|-----|
| `/agent-send <target> --stdin <<'BODY'…BODY` | Send a **request** (heredoc body, expansion-safe — preferred). The peer acts and replies. |
| `/agent-send <target> "<body>"` | Same, inline body. Fine for short, metachar-free one-liners only. |
| `/agent-send <target> … --reply` | Send a **reply** (terminal; no response expected — breaks ping-pong loops). |
| `/agent-send <target> … --followup` | Send a **followup**: a threaded message that **does** expect a response. Use instead of `--reply` when your reply asks the peer to act. |
| `/agent-broadcast --stdin <<'BODY'…BODY` | Fan out one message to **all live peers** (`--exclude a,b`, `--followup`, `--dry-run`). High blast-radius — needs explicit user authorization. |
| `/agent-fanout status` / `… msg --role <r>` / `… merge-down` / `… restart` / `… resume-errored` | Fleet orchestration: read-only fleet snapshot, role-targeted message fan-out, canned post-push sync, idle-gated force-restart (`claude --continue --name`, always confirmed), and `resume-errored` (manually nudge rate-limited/`StopFailure` agents to continue — the same retriable-only sweep also runs continuously in the coordinator's always-on `inbox-watcher`, throttled). High blast-radius — see the skill. |
| `/agent-msg <sender> <filename> [reply\|followup]` | Receiver-side handler. Invoked automatically when another agent's `tmux send-keys` (or the drain) lands in your prompt buffer — you never type this yourself. |
| `/agent-rename <new-name>` | Rename this agent everywhere — registry, tmux pane title, Claude session name, and (cc/feature only) the tmux window. |

## Window names + layouts
<!-- tags: tmux · layout · multi-monitor -->

_An agent's identity is its **pane id**, so the fleet's tmux topology is free to change under it — one script owns both the window labels and the rearranging._

- **Pane id is the identity token.** `~/.claude/running-agents/<name>.<pid>` holds `$TMUX_PANE`; delivery is `send-keys -t %N`, liveness is `tmux list-panes -a`, and all coordination state is on the filesystem. **Nothing targets a window name, window index, session, or client.**
- **`join-pane` moves a pane rather than recreating it**, and a pane id is stable for the pane's lifetime. So `fleet-layout.sh` can rebuild the whole topology around **live** agents — no restarts, no re-registration, and nudges never miss.
- **One tmux server, always.** Attach more clients; never spawn a second server. A second server restarts pane ids at `%0` (collision), `list-panes -a` can't see across servers, `agent-send.sh` would prune a live agent's registry entry, and `send-keys` could type into an unrelated pane. `FLEET_TMUX_SOCKET` exists only for `fleet-layout.test.sh`'s scratch server.

**Window order.** Every path ends in the same order: the coordinator, then the feature agents by agent number, then the review/test windows, then unrelated windows. `_order_windows` ranks each window from its residents and is idempotent — it emits nothing when the order already matches, which is what makes it safe on every `SessionStart`.

**Window naming.** `fleet-layout.sh name-windows` derives each window's label from **all** of its resident live agents — one agent → its name; several of one role → the plural (`features`); mixed roles → sorted and hyphenated (`review-test`); no agents → left alone. Because the name is a function of the whole pane set rather than of whoever spoke last, every agent computes the same answer and co-tenants cannot clobber each other. `register-agent.sh` (SessionStart) and `agent-rename.sh` both call it, so labels stay automatic.

**Layouts.** `fleet-layout.sh <single|dual|wide> [--dry-run]` rearranges the **feature** agents; the coordinator, the review/test window, and unrelated windows are never touched. Each agent occupies a *cell*: its claude pane on the left, its companion panes stacked to the right, split 60/40 (the top-right pane runs `WORKFLOW_CELL_COMMAND` if you set one — empty by default, so it is just a shell).

| Layout | Shape | For |
|---|---|---|
| `single` | one window per feature agent, in the home session | the laptop — your hand-arranged panes are respected |
| `dual` | 2 agents per window × 2 windows (`features-1`, `features-2`), stacked | a conventional second monitor |
| `wide` | all feature agents in one `features` window, 2×2 of cells | the ultra-wide |

- **`wide` and `dual` live in a DEDICATED tmux session** (default name `wide`; override via `WORKFLOW_FLEET_EXT_SESSION`, legacy alias `WORKFLOW_FLEET_WIDE_SESSION`), not a grouped one. Grouped sessions share the window list by construction, so the feature windows would remain tabs in the laptop's window. `move-window` relocates a window between sessions on one server **without changing pane ids** — delivery, liveness, and the registry are all unaffected. Both modes open the second-monitor iTerm window themselves and move the windows across; `single` brings them home and closes it.
- **Never type into a freshly-opened terminal window.** If your shell rc auto-attaches to tmux (e.g. it ends with `exec tmux new-session -A -s main`), a new interactive shell is *already* a tmux client of the home session — `write text`/`send-keys` would land in whatever pane that session has active, potentially an agent's Claude prompt. `attach` spots the new client by its `tty` and uses `tmux switch-client` instead.
- Companion panes are attributed by matching a pane's cwd against the agent's `~/.claude/agents/<name>.cwd` (**or a subdirectory of it**), excluding every other agent's claude pane. Set the `@fleet-layout-skip` pane option on a pane you parked in a worktree yourself and want left alone.
- **Caveat:** a pane scrolled up into copy-mode suppresses the live nudge (`pane_in_mode`). The message still drains via the durable mailbox, but a parked agent idles until re-nudged (capped by `WORKFLOW_MAX_REDELIVER`). More monitors means more scrolled panes.

**Boot (crash recovery).** `fleet-layout.sh boot [--dry-run]` brings the fleet up from cold: it enumerates agent worktrees from the machine-local manifest (path from `fleet_manifest_path` — `WORKFLOW_WORKTREES_MANIFEST`, else `~/.config/<main-clone-basename>-worktrees.json`; entries with an `agent` field; `active: false` parks a lane), skips self and live registrations (name-keyed AND cwd-corroborated — a live registration or occupied pane at the worktree counts whatever its name, so transient auto-names can't cause a double-launch), sweeps dead same-name registry entries, creates missing windows in canonical order, and types `claude --continue` (or plain `claude` for a worktree with no prior sessions) **only into panes that very run created** — a pre-existing window named for the agent is reported `window-exists` and left untouched, because its pane state is unknown. Each window boot creates gets the full **cell** : claude full-height on the left (~60%), a right column stacked with the configured companion command top-right (`WORKFLOW_CELL_COMMAND`; empty ⇒ nothing is keyed) and a shell at the prompt bottom-right — panes sized at creation time and keyed **only via ids captured from that same run's splits**; a failed split degrades loudly (reported + non-zero exit) without losing the claude launch. Names/order then converge through each booting agent's own SessionStart registration (which calls `name-windows`). Resume prompts are answered by the human — boot never blind-keys a pane. The manifest failure model is loud: corrupt/missing manifest → non-zero exit, never a silent empty fleet. Full contract: [`fleet-layout` skill](../skills/fleet-layout/SKILL.md).

**Down (clean stop).** `fleet-layout.sh down [--dry-run] [--force]` is boot's inverse and the fleet's only sanctioned kill path: it matches live registrations to manifest worktrees **by path, never by name** (transient auto-names would blind a name-keyed sweep), kills each matched agent's claude pane + attributed companions (`@fleet-layout-skip` and co-tenant panes survive; never a pid, never a worktree), gates on the busy marker (`--force` overrides BUSY only — never a skip marker), and **verifies every kill by observation** before claiming `downed`. Every guard input fails closed into a loud non-zero refusal — exit 0 means every non-self entry is downed-and-verified or probe-confirmed not running. `down` + `boot` is the sanctioned full-fleet restart (sessions recover via `claude --continue`; resume prompts stay human-answered). Full contract: [`fleet-layout` skill](../skills/fleet-layout/SKILL.md).

**Where the home session comes from.** `boot` creates its windows in `WORKFLOW_FLEET_HOME_SESSION`, and — the part that bites — **each agent's SessionStart runs `name-windows` in its own worktree**, a separate process that never sees boot's resolution. So the value is *persisted*, machine-locally: `/base-initialize` and `/base-setup` write it into the **gitignored** `.claude/workflow.config.local` (via `.claude/scripts/workflow-local.sh`), and `/add-worktree` **seeds that file into each new worktree** — a worktree's checkout carries only tracked files, so it would otherwise have none, and `_config.sh` resolves its root to the *worktree*. A worktree without it reads no base branch (solo mode) and no home session (window ordering silently does nothing). Boot still falls back to the invoking client's session and says so, but that backstop only fixes boot — not the agents.

## Conversation shapes worth knowing

Beyond ad-hoc requests, two structured exchanges ride this transport:

- **Plan review** (`/todo` start step 3): a feature agent sends `PLAN REVIEW REQUEST: <ID> …` with the plan content inline to a review-role agent (discovered via `agent-fanout.sh status`, ROLE = `review`); the reviewer replies `--reply` with **`PLAN GREEN`** or numbered blocker/suggestion findings; the outcome lands in the TODO's `plan_review:` frontmatter (gen:todos-validated). Read-only, pre-implementation.
- **Diff review** (workflow step "STOP for review"): the post-implementation `/base-pr` audit request; the reviewer replies **`GREEN LIGHT`** or blockers/nits with `file:line`. The two verdict tokens are deliberately distinct.

## Auto-discovery

A sending agent finds its own name by scanning `~/.claude/running-agents/` for the file whose **content** matches its own `$TMUX_PANE`. This works in any subprocess of Claude (the Bash tool, hooks, etc.) because `$TMUX_PANE` is inherited reliably; `$PPID` is not (intermediate shells in the Bash tool chain confuse it).

## Caveats

- **The register-agent SessionStart hook lives at user-level by design.** Project-local `SessionStart` hooks fire fine in current Claude Code (an older limitation rejected them, which is why this wiring predates it; `cc-watcher-keepalive.sh` runs project-locally on SessionStart today). Registration stays user-level deliberately: `~/.claude/settings.json` references `$CLAUDE_PROJECT_DIR/.claude/hooks/register-agent.sh`, so it runs in every project the engineer launches `claude` in — and when the script doesn't exist there, the hook is a clean no-op.
- **Single-line slash command on delivery.** `tmux send-keys` treats newlines as Enter, which would submit the prompt early. The body lives in a file, but the slash command itself is one line — no special characters to escape in the wire format.
- **Body corruption via argv expansion — use `--stdin`.** When a *sending* agent builds the `agent-send` call with the body inside double quotes, the sender's own shell expands backticks and `$(...)` in the body *before* `agent-send` runs, silently corrupting the message (this mangled a code review in practice). Always prefer `agent-send <target> --stdin <<'BODY' … BODY` (quoted heredoc) for anything that might contain shell metacharacters. The inline `"<body>"` form is for short, metachar-free one-liners only.
- **Mid-turn delivery queues, then drains.** If the recipient is mid-response when the nudge arrives, the slash command sits in their prompt buffer and fires at the start of the next turn. If the nudge fails entirely, `drain-inbox.sh` re-injects it from the durable mailbox at the next `Stop`. Either way the message lands; only latency varies.
- **Human typing collides.** If the human is keying into the target pane when `tmux send-keys` fires, bytes interleave and the nudge may be garbled. Property of `send-keys`; nothing this layer can fix — but the drain still delivers the message from the mailbox regardless, so a garbled nudge is not a lost message.
- **No cross-machine.** Everything is local — registry, inbox, and tmux are all on the same host. Multi-machine fan-out would need a different transport.

## Adding a new agent message type

The current protocol is `request` (`req`), `reply` (`rep`), and `followup` (`fwd`). To add another (say, `cancel` to abort a long-running task):

1. Extend `agent-send.sh` to accept the new flag, encode the new `<kind>` token in the staged filename (`<uuid>.<self>.<kind>.txt`), and append the keyword after the path when delivering. Keeping the kind in the filename is what lets `drain-inbox.sh` reconstruct the right `/agent-msg` for a dropped nudge.
2. Update `agent-msg/SKILL.md` so the recipient's branching logic recognizes the new type, and teach **both** `drain-inbox.sh` and `inbox-watcher.sh` to map the new `<kind>` token to its delivery keyword. Add a case to `drain-inbox.test.sh`. Keep `req`/`rep`/`fwd` semantics intact.
3. If the new type changes the banner's visual style (different glyph, header text), update both the banner template and the description so the human can spot it at a glance.

The wire format is intentionally positional and minimal — adding a fourth or fifth keyword is cheap; structural changes (e.g. moving to a JSON envelope) would require updating every caller.

## Deferred / future work

Surfaced but intentionally **not** built yet (they're protocol rewrites better done as their own reviewed change, not bolted onto the current positional format):

- **JSON envelope.** Replace the positional `<uuid>.<sender>.<kind>` filename + trailing keyword with a small JSON sidecar (`{from, kind, thread, ts, …}`). Would centralize metadata (today `kind` lives in both the filename and the wire keyword) and make new fields one-touch instead of editing every parser. The cost is touching every caller (`agent-send`, `agent-broadcast`, `drain-inbox`, `inbox-watcher`, the `agent-msg` skill).
- **Correlation IDs / threading.** A short thread id echoed across a request → reply/followup chain, surfaced in the banner, so multi-message exchanges are unambiguous (we saw three copies of one review in flight with only prose to tell them apart). Depends on the envelope above to carry it cleanly.
- **Delivery acknowledgement.** `agent-send` reports *staged + nudged*, not *processed*. An optional ack (recipient pings back on consume) would let a sender know a message actually landed, and feed a real dead-letter path. Also wants the envelope for the correlation id.
